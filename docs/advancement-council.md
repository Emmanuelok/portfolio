# The advancement council

The advancement council is a governed multi-agent capability that answers a
different question from the focused and coordinated reviewers. Those reviewers
assess an artifact. The council reads the whole project record and proposes what
must happen next for the project to advance responsibly.

Like every other AI path in this platform, the council is proposal-only. It
cannot apply a revision, publish work, change a project, or approve an Atlas
phase gate. A person performs each of those actions.

## Why it is structured as a council

A single reviewer asked "what should we do next?" tends to produce plausible,
agreeable recommendations, because nothing in the request forces it to
distinguish a step the project record supports from one it merely permits. The
council structure exists to create that pressure:

1. **Survey.** One agent establishes the project's current position from the
   record alone: what the record establishes, what it assumes without support,
   what is missing, and where entries contradict each other. It is forbidden
   from proposing next steps, so grounding happens before advocacy.
2. **Proposal.** Each selected council member proposes exactly one move through
   a distinct lens. A member must cite the evidence and decision identifiers its
   move rests on, or set `unsupported` and say plainly that the record holds no
   support.
3. **Challenge.** Every move is handed to an independent challenger that did not
   write it, with the mandate to refute it. The challenger verifies that each
   cited identifier exists, that the move assumes no validation the record
   lacks, that it is the smallest responsible step, and that its stated outcome
   would actually change a decision. It defaults to `refuted` or `qualified`
   under uncertainty.
4. **Synthesis.** The chair ranks the surviving moves into the order a person
   should take them and assesses gate readiness against the phase's acceptance
   criteria.

The challenge stage is the reason the output is worth reading. A move that
cites an evidence identifier absent from the record is refuted rather than
ranked, which is verified by test 4 in `tests/advancement-council.test.ts`.

## Lenses

Council members are lenses on advancement, not the specialist review roles used
by the coordinated reviewer:

| Lens | Mandate |
| --- | --- |
| `evidence-gap` | What must be known before the next step is defensible. |
| `smallest-test` | The smallest responsible test that would change a decision. |
| `system-risk` | The dependency or failure path most likely to invalidate the direction. |
| `delivery-path` | The bounded work that would produce a reviewable artifact. |

At least one lens is required and at most four run in a session.

## Gate readiness is an assessment, not a decision

The chair returns one of `not-ready`, `evidence-incomplete`, or
`ready-for-human-decision`, with the criteria it considers satisfied and
missing. `ready-for-human-decision` means the record appears to support putting
the gate to a person. It never records a decision, and the phase gate in Canvas
remains a human-only action. A record holding no evidence is never assessed
above `not-ready`.

## Streaming

`POST /api/intelligence/council` responds with newline-delimited JSON stage
events rather than one terminal payload, so Canvas shows the council working:
the survey lands, each proposal appears as its member returns, and each verdict
attaches to its own move. Each lens runs its own propose-then-challenge chain,
so a challenge starts as soon as its move exists instead of waiting for the
slowest member.

Event stages are `accepted`, `survey`, `proposal`, `challenge`, `complete`, and
`failed`, validated by `councilStageEventSchema`.

## Boundaries and prompt isolation

All project material reaches the models inside high-entropy, per-request nonce
boundaries generated by the server. Boundary-looking text inside the serialized
JSON stays untrusted, so material copied into a project cannot forge the end of
its own envelope. Downstream stages fence the survey, the proposed move, and
the challenge input separately.

Council agents have no tools: no browsing, code execution, deployment,
messaging, or external access of any kind.

Requests are screened for credential-shaped strings before any provider call and
rejected with `credential_detected` rather than forwarded.

## Degradation

The council degrades honestly rather than failing opaquely:

- **No provider configured** — the session runs the deterministic local council,
  which reads record structure only and says so in its boundaries and in the
  interface.
- **The survey fails** — the whole session falls back to the local reading.
- **One member fails** — the session continues, and the result discloses how
  many members did not return a proposal.
- **A challenge fails** — the move is marked `qualified`, never `upheld`. An
  unchallenged move is never presented as having survived challenge.
- **The synthesis fails** — moves are ranked by challenge verdict, and gate
  readiness reports that it was not assessed.

Each of these paths is covered by `tests/advancement-council.test.ts`.

## Cost and access

A session costs up to `2 + 2 × lenses` provider calls, capped at
`MAX_COUNCIL_PROVIDER_CALLS`. Because that is the most expensive operation in
the platform, the route requires an authenticated session, organization
membership, and a write role; viewers cannot start one. Credits are reserved
through the same distributed usage policy as every other provider path, and the
project snapshot must match the saved cloud project before any provider work
begins.

## Configuration

The council reuses the intelligence model routes unless it is given its own:

```
KINGXFORD_COUNCIL_STANDARD_MODEL=
KINGXFORD_COUNCIL_STANDARD_FALLBACK_MODELS=
KINGXFORD_COUNCIL_DEEP_MODEL=
KINGXFORD_COUNCIL_DEEP_FALLBACK_MODELS=
```

When these are unset the council falls back to the
`KINGXFORD_INTELLIGENCE_*` routes, then to the `KINGXFORD_CREATIVE_*` routes.
As with every other provider path, an unresolvable model slug means sessions
silently serve the local reading; verify the configured slugs against the live
gateway catalog before launch.
